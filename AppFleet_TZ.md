# Техническое задание: AppFleet

**Версия документа:** 0.2  
**Дата:** 30.08.2026

## 1. Назначение

**AppFleet** — настольное приложение для Windows, которое позволяет по ссылкам на публичные GitHub-репозитории:

- добавлять приложения в личный список;
- устанавливать приложения из GitHub Releases;
- определять наличие новых версий;
- обновлять установленные приложения после отдельного подтверждения пользователя;
- обновлять сам AppFleet.

Основная задача — убрать ручную последовательность «открыть репозиторий → найти релиз → выбрать файл → скачать → удалить старую версию → установить новую».

## 2. Границы первой версии

### 2.1. Поддерживается

- Windows 10 и Windows 11, только x64.
- Публичные репозитории GitHub.
- Добавление репозитория пользователем по ссылке.
- Stable-релизы GitHub Releases; draft и prerelease по умолчанию игнорируются.
- Установщики `.exe`, `.msi` и переносимые сборки `.zip`.
- Полностью управляемая установка и обновление приложений, соответствующих документу `Windows_Installer_Standard.md`.
- Best-effort-режим для сторонних репозиториев.
- Ручной запуск AppFleet. Фоновая работа, трей и планировщик Windows не используются.
- Отдельное подтверждение установки или обновления каждого приложения.

### 2.2. Не входит в первую версию

- Приватные репозитории и авторизация GitHub.
- Источники, отличные от GitHub Releases.
- Автоматическое обновление без подтверждения пользователя.
- Фоновая проверка, автозапуск вместе с Windows и уведомления из трея.
- ARM64 и 32-разрядные версии Windows.
- Гарантированная тихая установка произвольных сторонних EXE-файлов.
- Автоматическое удаление приложения при удалении его из списка AppFleet.
- Поддержка Microsoft Store, WinGet, Scoop и Chocolatey.

## 3. Технологические требования

- Язык: Java.
- Рекомендуемая версия: Java 21 LTS, x64.
- Интерфейс: JavaFX.
- Система сборки: Gradle Wrapper.
- HTTP-клиент: стандартный `java.net.http.HttpClient` либо одна выбранная библиотека без дублирования HTTP-стека.
- JSON: Jackson.
- Логирование: SLF4J + Logback.
- Дистрибутив содержит собственную Java Runtime; установленная в Windows Java не требуется.
- Сборка приложения: `jlink`/`jpackage app-image`, конечный установщик — Inno Setup EXE по единому стандарту.

Если в создаваемом репозитории уже закреплены совместимые версии JavaFX, Gradle или библиотек, допускается использовать их, но выбранные версии должны быть зафиксированы и воспроизводимо собираться через Gradle Wrapper.

## 4. Общий сценарий работы

1. Пользователь вручную запускает AppFleet.
2. AppFleet сначала проверяет обновление самого себя.
3. Если доступно обновление AppFleet, пользователю показывается отдельное подтверждение.
4. После завершения либо отказа от самообновления AppFleet проверяет все добавленные репозитории.
5. В главном окне отображается состояние каждого приложения.
6. Для каждого приложения пользователь отдельно нажимает `Установить` или `Обновить`.
7. Перед скачиванием AppFleet показывает версию, файл, размер, описание релиза и источник.
8. Если приложение запущено, AppFleet предлагает закрыть его автоматически.
9. После подтверждения выполняется скачивание и установка.
10. После завершения строка приложения обновляется без обязательного перезапуска AppFleet.

## 5. Пользовательский интерфейс

Интерфейс строится по схеме современного настольного приложения Windows: фиксированная левая боковая панель, командная панель над содержимым и строгий табличный список приложений. Карточное представление не используется.

### 5.1. Компоновка главного окна

Главное окно состоит из трёх областей:

1. Верхняя строка заголовка с названием `AppFleet` и стандартными кнопками окна Windows.
2. Фиксированная левая боковая панель.
3. Правая рабочая область, содержимое которой зависит от выбранного пункта боковой панели.

Левая панель и верхняя командная панель не должны прокручиваться вместе со списком приложений. Размеры и расположение элементов должны адаптироваться при изменении размера окна, но приложение не обязано превращаться в мобильный интерфейс.

### 5.2. Левая боковая панель

В верхней части панели находятся пункты навигации:

- `Приложения` — основное представление, выбранное по умолчанию;
- `Журнал` — история проверок, скачиваний, установок и ошибок.

В нижней части той же панели постоянно размещаются два переключателя и информация о версии:

- `Повторно запускать приложение после обновления, если оно было запущено` — включено по умолчанию;
- `Удалять скачанные установщики после успешной установки` — включено по умолчанию;
- `Версия AppFleet: <version>` — информационное поле без возможности редактирования.

Отдельного пункта `Настройки`, отдельной страницы и отдельного окна настроек быть не должно. Других пользовательских настроек в первой версии нет. Тема интерфейса автоматически следует системной теме Windows.

Если высоты окна недостаточно, навигация остаётся сверху, блок переключателей и версии — снизу, а между ними допускается свободная область. Подписи переключателей могут переноситься на несколько строк, но не обрезаться.

### 5.3. Представление «Приложения»

Над списком располагается командная панель:

- заголовок `Приложения`;
- время последней проверки и количество добавленных репозиториев;
- кнопка `Проверить`;
- основная кнопка `Добавить репозиторий`.

При обычном запуске проверка обновлений начинается автоматически. Кнопка `Проверить` запускает повторную проверку вручную.

Ниже находится строгий табличный список. Минимальный состав колонок:

- `Приложение` — название и адрес `OWNER/REPOSITORY`;
- `Состояние`;
- `Установленная версия`;
- `Последняя версия`;
- `Дата релиза`;
- `Файл` — выбранный asset;
- `Размер`;
- `Действие`;
- контекстное меню `…`.

Кнопка основного действия находится непосредственно в строке приложения: `Установить`, `Обновить`, `Повторить` либо недоступное состояние `Актуально`.

Заголовок таблицы остаётся видимым при вертикальной прокрутке. Ширина таблицы не должна искусственно сжимать колонки до нечитаемого состояния.

Область списка должна поддерживать обе независимые прокрутки:

- вертикальную — когда строки не помещаются по высоте;
- горизонтальную — когда колонки не помещаются по ширине.

Полосы прокрутки относятся только к области таблицы. Левая панель, заголовок страницы и командная панель остаются на месте. Горизонтальная полоса находится у нижней границы области списка и позволяет добраться до всех колонок и действий.

Строка приложения должна показывать:

- название;
- владельца и имя GitHub-репозитория;
- установленную версию либо статус `Не установлено`/`Версия не определена`;
- последнюю доступную версию;
- статус;
- дату релиза;
- выбранный файл релиза;
- размер файла;
- кнопку основного действия;
- меню удаления приложения из списка и повторного выбора файла релиза.

Статусы:

- `Проверка`;
- `Не установлено`;
- `Установлена актуальная версия`;
- `Доступно обновление`;
- `Версия не определена`;
- `Релизы не найдены`;
- `Требуется выбрать файл`;
- `Ошибка проверки`;
- `Скачивание`;
- `Установка`;
- `Обновлено`;
- `Требуется действие пользователя`.

### 5.4. Представление «Журнал»

Пункт `Журнал` открывает в правой рабочей области хронологический лог процессов AppFleet. Это не отдельное окно.

Для каждой записи показываются:

- дата и время;
- приложение или репозиторий;
- операция;
- результат;
- короткое понятное описание.

Журнал должен отражать как минимум:

- запуск AppFleet и проверку его собственной версии;
- начало и окончание общей проверки репозиториев;
- результат проверки каждого репозитория;
- выбор asset;
- скачивание и проверку файла;
- попытку закрытия приложения;
- запуск и код завершения установщика;
- успешную установку или обновление;
- отмену пользователем;
- ошибку и её техническую причину.

Технические подробности конкретной записи раскрываются по нажатию и не перегружают основной список. Журнал поддерживает вертикальную прокрутку и сохраняется между запусками согласно правилам раздела 14.

### 5.5. Добавление репозитория

Пользователь вводит только ссылку одного из видов:

```text
https://github.com/OWNER/REPOSITORY
https://github.com/OWNER/REPOSITORY/
https://github.com/OWNER/REPOSITORY/releases
https://github.com/OWNER/REPOSITORY/releases/tag/v1.5.0
```

AppFleet нормализует любую из этих ссылок до `OWNER/REPOSITORY`, проверяет существование публичного репозитория и запрашивает последний stable-релиз.

Если пользователь вставил ссылку на конкретный релиз `/releases/tag/<tag>`, тег используется только для распознавания исходной ссылки и не закрепляется за приложением. После добавления AppFleet всегда проверяет последний стабильный релиз репозитория. Например, ссылка на `v1.5.0` не должна мешать в дальнейшем обнаружить `v1.6.0`.

Дублирование уже добавленного репозитория запрещается. Вместо второй строки AppFleet открывает существующее приложение в списке.

## 6. Получение сведений о релизе

### 6.1. Приоритет метаданных

1. Если в релизе есть `appfleet-manifest.json`, использовать его после проверки схемы.
2. Если манифеста нет или он некорректен, выполнить автоматический анализ assets.
3. Автоматически созданные решения нельзя выдавать за гарантированные: для стороннего репозитория интерфейс должен явно показывать выбранный файл.

### 6.2. Выбор assets без манифеста

Из рассмотрения исключаются:

- автоматически добавленные GitHub архивы исходников;
- файлы с признаками `source`, `sources`, `src`, `symbols`, `debug`, `javadoc`;
- файлы для Linux и macOS;
- ARM/ARM64 и x86-файлы;
- контрольные суммы, подписи и текстовые документы как установочные пакеты.

Приоритет поддерживаемых файлов:

1. Windows x64 `.exe` с признаками `setup`, `installer` или `install`;
2. Windows x64 `.msi`;
3. Windows x64 `.zip` с признаками `portable`, `win`, `windows` или `x64`;
4. остальные `.exe`, `.msi` и `.zip`, если они не противоречат платформе.

Если после фильтрации остался один уверенно подходящий файл, он выбирается автоматически.

Если осталось несколько равнозначных файлов, AppFleet один раз показывает их пользователю. Для каждого варианта отображаются имя, тип, размер и архитектура, определённая по имени. Выбор запоминается не как точное имя текущего файла, а как правило сопоставления последующих релизов. Если в новом релизе правило перестало давать единственный результат, выбор запрашивается повторно.

Запрещается безусловно выбирать первый asset релиза.

### 6.3. Версии

- Для наших приложений используется SemVer без префикса либо с префиксом `v`: `1.4.0` и `v1.4.0` эквивалентны.
- Для сторонних приложений сначала используется нормализованный GitHub tag.
- Сравнение SemVer выполняется численно, а не лексикографически.
- Если версия стороннего релиза не разбирается однозначно, AppFleet сравнивает release tag на точное равенство и не делает предположений о том, какая версия новее. Пользователю показывается предупреждение.

## 7. Определение установленной версии

### 7.1. Наши стандартизированные приложения

Версия и параметры установки определяются по реестру, который заполняется стандартным установщиком:

```text
HKCU\Software\PashaApps\<AppId>
```

Минимальный набор значений указан в `Windows_Installer_Standard.md`.

### 7.2. Сторонние приложения

Для сторонних приложений допускаются следующие источники, в порядке приоритета:

1. состояние установки, ранее успешно выполненной самим AppFleet;
2. точное сопоставление с записью Windows Uninstall Registry;
3. версия файла основного EXE, если его путь достоверно известен.

Если уверенного сопоставления нет, отображается `Версия не определена`. AppFleet не должен угадывать приложение по частичному совпадению коротких названий и не должен удалять неизвестную старую установку.

Для приложения, впервые установленного через AppFleet, сохраняются GitHub release tag, asset ID, тип пакета, путь установки, результат запуска установщика и время операции.

### 7.3. Иконка установленного приложения

Если AppFleet знает путь к основному EXE, он извлекает иконку напрямую из встроенных ресурсов этого EXE. Файл открывается как ресурсный модуль без загрузки и выполнения кода. Приоритетный путь: `RT_GROUP_ICON` → выбор варианта до `256×256` → соответствующий `RT_ICON`. Иконка выводится в естественном размере, не больше размера элемента интерфейса; искусственно увеличивать малую иконку запрещено.

Windows Shell допускается только как резервный источник для стороннего EXE без читаемого встроенного ресурса. Shell-кэш не должен быть основным источником: он может содержать устаревшую или низкокачественную копию. При невозможности получить нативную иконку AppFleet показывает буквенную заглушку. Для стандартизированных приложений требования к многомасштабной встроенной иконке определяет `Windows_Installer_Standard.md`.

## 8. Установка и обновление

### 8.1. Общее подтверждение операции

Для каждого приложения подтверждение показывается отдельно и содержит:

- название и репозиторий;
- текущую версию;
- устанавливаемую версию;
- имя и размер файла;
- описание релиза или ссылку на него;
- сведения о контрольной сумме и цифровой подписи;
- предупреждение, если установка стороннего EXE будет интерактивной.

### 8.2. Скачивание

- Скачивать только по HTTPS со ссылок, полученных через GitHub API.
- Использовать отдельный временный каталог операции.
- Поддерживать отображение прогресса и отмену до запуска установщика.
- Не считать файл доверенным только из-за расширения.
- Не собирать командную строку конкатенацией пользовательского текста.

### 8.3. Проверка файла

Для наших приложений наличие SHA-256 обязательно. Хэш берётся из `appfleet-manifest.json` либо отдельного asset с расширением `.sha256` и проверяется до запуска.

Для стороннего приложения:

- при наличии SHA-256 он проверяется;
- при наличии Authenticode-подписи проверяется её валидность;
- отсутствие подписи или контрольной суммы не блокирует установку, но явно показывается пользователю;
- недействительная подпись или несовпадение хэша блокируют запуск.

### 8.4. Работа с запущенным приложением

Если известен процесс приложения и он запущен, перед установкой показывается предложение `Закрыть автоматически`.

- При согласии сначала запрашивается штатное закрытие окна/процесса.
- Принудительное завершение допускается только после отдельного дополнительного подтверждения.
- При отказе пользователя операция установки отменяется либо передаётся интерактивному установщику, если он способен сам обработать запущенное приложение.
- Системные и не относящиеся к выбранному приложению процессы завершать запрещено.

### 8.5. Типы пакетов

#### Стандартный Inno Setup EXE

Запускается с параметрами, указанными в манифесте. Для наших приложений используется:

```text
/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS
```

Перезапуск приложения после обновления выполняет AppFleet, если пользователь выбрал соответствующий вариант.

#### Сторонний EXE

AppFleet не пытается угадывать параметры тихой установки. EXE запускается интерактивно. Полностью тихий режим допустим только при наличии валидного `appfleet-manifest.json` с явно заданными аргументами.

#### MSI

Для установки:

```text
msiexec.exe /i <file.msi> /passive /norestart
```

Код завершения Windows Installer должен быть обработан. Код, требующий перезагрузки, показывается пользователю, но AppFleet самостоятельно Windows не перезагружает.

#### ZIP

ZIP поддерживается только как управляемая AppFleet переносимая установка:

- архив распаковывается в `%LOCALAPPDATA%\Programs\AppFleetManaged\<owner>\<repository>`;
- защита от Zip Slip обязательна;
- перед обновлением новая версия распаковывается во временный соседний каталог;
- после проверки содержимого текущая папка переименовывается в резервную, а новая — в рабочую;
- при ошибке выполняется откат;
- после успешного запуска резервная папка может быть удалена;
- пользовательские данные внутри заменяемой папки не гарантируются и об этом показывается предупреждение.

## 9. Самообновление AppFleet

Самообновление обязательно и проверяется раньше остальных приложений.

Алгоритм:

1. AppFleet запрашивает последний stable-релиз собственного репозитория.
2. Сравнивает его версию с текущей.
3. Показывает отдельное подтверждение обновления.
4. Скачивает `AppFleet-Setup-<version>-x64.exe` во временную папку.
5. Обязательно проверяет SHA-256 и соответствие `appfleet-manifest.json`.
6. Сохраняет маркер ожидаемого обновления и текущий список незавершённых проверок.
7. Запускает установщик:

```text
/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /RESTARTAPPLICATIONS
```

8. Завершает собственный процесс.
9. Независимый процесс Inno Setup заменяет файлы AppFleet и запускает новую версию.
10. Новая версия проверяет маркер, удаляет временные файлы и заново проверяет список приложений.

Защита от цикла:

- сохранять целевую версию и число попыток;
- не повторять автоматически один и тот же неудавшийся переход версии в рамках одного запуска;
- после неудачи показывать ошибку и оставлять работоспособной прежнюю версию;
- не считать обновление успешным до запуска новой версии и проверки её номера.

Самообновление также требует согласия пользователя. Отказ не мешает просмотреть остальные обновления, если текущая версия AppFleet совместима с используемой схемой манифеста. Если релиз требует более новую минимальную версию AppFleet, несовместимые операции блокируются с понятным объяснением.

## 10. Хранение данных

```text
Программа:  %LOCALAPPDATA%\Programs\PashaApps\AppFleet
Настройки:  %APPDATA%\PashaApps\AppFleet
Кэш/логи:  %LOCALAPPDATA%\PashaApps\AppFleet
Временные:  %TEMP%\AppFleet\<operation-id>
```

Минимальные локальные файлы:

```text
repositories.json
settings.json
operations.json
logs/appfleet.log
```

В `settings.json` сохраняются только два пользовательских параметра:

```json
{
  "restartPreviouslyRunningApp": true,
  "deleteInstallerAfterSuccess": true
}
```

Отсутствующие значения получают значение `true`. Версия AppFleet не является настройкой и берётся из метаданных самой сборки.

Для каждого репозитория сохраняются:

- `owner` и `repository`;
- канонический URL;
- выбранное правило asset;
- последняя известная установленная версия;
- последний установленный asset ID;
- тип установки;
- сведения для обнаружения процесса и установки, только если они определены достоверно;
- время и результат последней проверки;
- версия схемы данных.

Запись JSON выполняется атомарно через временный файл и замену. Повреждение одного файла не должно приводить к молчаливой потере всего списка; требуется резервная копия последней корректной версии.

## 11. GitHub API

- Использовать официальное GitHub REST API.
- Указывать собственный `User-Agent`.
- Корректно обрабатывать rate limit и показывать время возможного повторения.
- Использовать `ETag`/`If-None-Match` для повторных проверок.
- Не парсить HTML-страницы GitHub как основной способ получения релизов.
- Не требовать GitHub token в первой версии.
- Не логировать временные URL скачивания целиком, если они содержат служебные параметры.

## 12. Ошибки и восстановление

Пользователь должен получить понятное сообщение как минимум в случаях:

- репозиторий не существует или не публичный;
- GitHub недоступен;
- превышен API rate limit;
- stable-релиз отсутствует;
- подходящий Windows x64 asset не найден;
- найдено несколько assets и требуется выбор;
- не удалось определить установленную версию;
- недостаточно места;
- скачивание прервано;
- SHA-256 не совпал;
- цифровая подпись недействительна;
- приложение не удалось закрыть;
- установщик завершился с ошибкой;
- MSI запросил перезагрузку;
- ZIP не удалось безопасно заменить или откатить;
- самообновление AppFleet не завершилось.

Технические подробности сохраняются в журнале, но основной текст ошибки должен объяснять пользователю, что произошло и что можно сделать.

## 13. Безопасность

- Принимать только ссылки на `github.com` и ответы официального GitHub API.
- Запрещать выход архивов и временных файлов за разрешённые каталоги.
- Проверять свободное место до распаковки и установки.
- Не выполнять строки из манифеста через shell; использовать массив аргументов `ProcessBuilder`.
- Разрешать в манифесте только известные типы установщиков и ограниченный набор полей.
- Не хранить и не запрашивать пароли.
- Не запрашивать права администратора самому AppFleet. Повышение прав допускается только Windows для конкретного стороннего установщика.
- Не удалять каталоги, путь которых не был предварительно нормализован и подтверждён как принадлежащий управляемому приложению.

## 14. Журналирование

Логировать:

- запуск и версию AppFleet;
- начало и результат проверки репозитория;
- решение о выборе asset;
- начало, отмену и завершение скачивания;
- результат проверки хэша и подписи;
- запуск установщика без секретных параметров;
- код завершения;
- самообновление и восстановление после него;
- источник и фактический размер каждой иконки установленного приложения; для резервного источника — причину перехода к нему;
- ошибки с stack trace.

Ротация технических файлов: не более 10 файлов по 5 МБ. Пользовательский журнал операций хранится в структурированном виде, открывается через пункт `Журнал` в левой панели и переживает перезапуск AppFleet. Отображаемые пользователю сообщения должны оставаться понятными, а stack trace и остальные технические подробности показываются только при раскрытии записи.

## 15. Критерии приёмки

1. На чистой Windows 10/11 x64 AppFleet устанавливается без отдельно установленной Java.
2. После ввода корректной ссылки публичный репозиторий появляется в списке.
3. Принимаются ссылка на корень репозитория, `/releases` и прямая ссылка `/releases/tag/<tag>`.
4. Прямая ссылка на старый релиз нормализуется до `OWNER/REPOSITORY`, после чего AppFleet обнаруживает более новый стабильный релиз.
5. Дубликат ссылки не создаёт вторую строку приложения.
6. Репозиторий с одним подходящим asset выбирается автоматически.
7. При нескольких подходящих assets пользователь один раз выбирает файл, а правило применяется к следующему релизу.
8. Наше приложение с `appfleet-manifest.json` устанавливается с нуля в тихом режиме.
9. AppFleet распознаёт установленную по стандарту версию через реестр.
10. При наличии новой версии показываются текущая и новая версии, описание и размер.
11. Без отдельного подтверждения установка или обновление не начинается.
12. При запущенном приложении предлагается автоматическое закрытие.
13. При включённом параметре ранее запущенное приложение автоматически запускается после успешного обновления.
14. При включённом параметре успешно использованный установщик удаляется.
15. Настройки обновляемого приложения сохраняются.
16. Несовпадение SHA-256 блокирует запуск файла.
17. Сторонний EXE без манифеста запускается интерактивно, без угаданных silent-аргументов.
18. MSI запускается через `msiexec` и его код возврата корректно отображается.
19. ZIP защищён от Zip Slip и откатывается при ошибке замены.
20. AppFleet находит собственное обновление раньше других, обновляется внешним установщиком и запускает новую версию.
21. Отмена самообновления не приводит к закрытию программы или циклу запросов.
22. При ошибке сети список репозиториев и последние известные версии не теряются.
23. Удаление приложения из списка не удаляет установленное приложение.
24. После перезапуска сохраняются репозитории, выбранные assets, два пользовательских параметра и история последних операций.
25. Интерфейс содержит фиксированную левую панель, командную панель и табличный список без карточек.
26. Таблица приложений независимо прокручивается по вертикали и горизонтали; её заголовок остаётся видимым при вертикальной прокрутке.
27. Переключатели и версия AppFleet находятся в левой панели; отдельного окна или страницы настроек нет.
28. Пункт `Журнал` открывает в основной области сохранённую историю процессов и позволяет раскрыть технические подробности записи.
29. Для установленного стандартизированного приложения AppFleet отображает иконку, напрямую извлечённую из встроенного ресурса его главного EXE; Shell используется только при недоступности этого ресурса.
