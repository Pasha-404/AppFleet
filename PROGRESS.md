## Этап 34 — безопасное закрытие приложений и UAC для сторонних EXE

**Реализовано:** закрыты D02 и P07 из `docs/CODE_REVIEW_GPT-6.md`. AppFleet сначала скачивает и проверяет replacement, и лишь затем рассматривает закрытие запущенного приложения. Цель выбирается только при точном совпадении с подтверждённым локальным EXE: совпадение одного имени файла в другом каталоге больше не является основанием для воздействия. Идентичность удерживается как `PID + время запуска + тот же EXE`; собственный процесс AppFleet исключается.

«Штатное закрытие» больше не вызывает `ProcessHandle.destroy()` (на Windows это `TerminateProcess`). Вместо этого выполняется ограниченный `EnumWindows` → `GetWindowThreadProcessId` → `WM_CLOSE` с `SendMessageTimeout`; приложение вправе отклонить этот запрос. Если оно осталось запущено, AppFleet сохраняет именно этот набор идентичностей и уже проверенный скачанный installer в continuation. Отдельное согласие пользователя применяет force-close только к тому же PID с тем же временем запуска и тем же EXE — без новой широкой переоценки. После успешной установки перезапуск возможен один раз и только по новому EXE, подтверждённому HKCU-registry detection; неизвестный или старый command line не возобновляется. UI использует типизированный `OperationOutcome`, а не поиск русской фразы в сообщении.

Для generic EXE, где `CreateProcess` вернул `ERROR_ELEVATION_REQUIRED (740)`, добавлен узкий Windows Shell adapter: он запускает только этот уже подтверждённый EXE через `runas`, показывает обычный UAC-диалог, получает process handle через `SEE_MASK_NOCLOSEPROCESS`, ждёт код завершения и освобождает handle. Отмена UAC сообщается отдельно и не считается успешной установкой. AppFleet не запускается от администратора и не угадывает silent-аргументы стороннего installer.

## Этап 35 — обратимая ZIP-установка и безопасное восстановление состояния

**Реализовано:** закрыты D04, P01 и P02 из `docs/CODE_REVIEW_GPT-6.md`. ZIP-пакет теперь проходит явную транзакцию: новый UUID-staging-каталог → безопасная распаковка → проверка ровно одного непустого EXE → атомарная подмена каталога → сохранение точного пути EXE/каталога/process name в state → удаление лишь старого backup. Пока state не сохранён, ошибка откатывает как обновление, так и первую установку; после сохранения state не откатывается, а неудачная очистка backup фиксируется как предупреждение. ZIP больше не оставляет state без пути к установленному EXE и умеет безопасно перезапустить именно проверенный новый EXE.

Временные каталоги manifest/install/self-update теперь создаются только как прямые UUID-потомки ограниченного root. Их очистка проверяет root, точное имя и UUID; marker самообновления никогда не удаляет произвольный сохранённый путь. Marker очищается и при неудачном самообновлении, поэтому новая попытка не блокируется. `AtomicJsonStore` восстанавливает основной файл из корректного backup, не перезаписывает последний корректный backup повреждённым primary, распознаёт JSON `null` как повреждение, а state-документы проверяют schema и обязательную идентичность репозитория до использования. Настройки и список репозиториев меняются в памяти только после удачной записи на диск.

## Этап 37 — корректные нативные иконки, инвалидация кэша и ограничение UI-обновлений

**Реализовано:** закрыты D12 и P05, а также измеримые части S02 из `docs/CODE_REVIEW_GPT-6.md`. Встроенная иконка EXE по-прежнему извлекается из PE-ресурсов без запуска целевого EXE, но AppFleet теперь сам выбирает подходящий *исходный* слой `RT_GROUP_ICON`: минимальный не меньше 48 px, либо наибольший из доступных маленьких. PNG-слой декодируется непосредственно через ImageIO, поэтому исходные размеры, прозрачные и полупрозрачные пиксели не проходят через GDI. Для legacy bitmap-слоя `CreateIconFromResourceEx` получает нулевые желаемые размеры (Windows сохраняет фактический размер ресурса); 32-bit BGRA сохраняет alpha, а AND-mask применяется только когда alpha отсутствует. В логах отдельно зафиксированы размер выбранного слоя, декодированный размер и ограничение размера карточки; UI не просит Windows растянуть маленькую иконку до 256 px.

Кэш иконок больше не привязан только к пути: ключ включает тип файла, размер, точное время изменения и file key. Внешняя замена EXE по тому же пути создаёт новую запись; отрицательный результат имеет ограниченное время повторной попытки; появление ранее отсутствующего EXE распознаётся сразу по новой file identity. После успешной установки или обновления UI явно инвалидирует иконки затронутых snapshots. Старое асинхронное извлечение не может заменить уже инвалидационную запись: callback сверяет именно текущий cache entry. PNG-кодирование переносится на worker и результат presentation-кодируется максимум один раз для записи кэша на FX thread, а не для каждой пересобранной карточки. Обновления прогресса скачивания coalesce до 10 в секунду с обязательным финальным событием, поэтому быстрый файл не ставит `Platform.runLater` на каждые 64 KiB.

Следующий этап — инварианты incremental-build/release и единый структурированный результат checksum/Authenticode (D15, D16, P03). Затем следуют фокусированные UI/UX-доработки, полная регрессия, существенное повышение версии и только после этого стандартный installer/публикация. ## Этап 38 — воспроизводимые build metadata, честная проверка файлов и целостный draft-release

**Реализовано:** закрыты D15, D16 и P03 из `docs/CODE_REVIEW_GPT-6.md`. `generateBuildInfo` теперь объявляет version, repository URL и AppId как Gradle inputs, поэтому изменение любого из них инвалидирует только необходимые ресурсы. Добавлена `verifyBuildInfo`: задача вскрывает реально собранный JAR и сверяет `appfleet-build.properties`, а не доверяет только имени installer/manifest. `verifyReleaseMetadata` требует ровно три release asset’а, непустой installer и SHA-256, пересчитанный по его фактическим байтам.

Введён общий типизированный результат проверки файла: SHA-256 (`проверен`/`не опубликован`) отдельно от Authenticode (`действительна`, `отсутствует`, `недействительна`, `не применяется`, verifier недоступен или завершился ошибкой). EXE, INNO и MSI проходят Authenticode; ZIP явно не проходит. Недействительная подпись по-прежнему блокирует запуск. Неподписанный файл, отсутствие SHA-256 или недоступность verifier не выдаются за «проверено» и становятся предупреждением согласно существующей permissive-policy. Обычная установка сохраняет результат в `OperationResult`, журнале и итоговом диалоге. Self-update проверяет тот же набор, показывает ожидаемую проверку до запуска, а фактическое предупреждение — перед выходом AppFleet.

Publisher перед любым API-вызовом сверяет локальные installer/checksum/manifest как единый набор. При продолжении draft он скачивает и хэширует каждый существующий asset, не принимает неожиданные имена, после upload повторно читает полный список asset’ов и сверяет все три содержимого. Несовпадение оставляет draft неопубликованным с инструкцией проверить/удалить его вручную; опубликованный release по-прежнему не меняется автоматически.

**Осталось:** версия остаётся `1.0.11`; installer, tag и GitHub Release на промежуточном этапе намеренно не создавались. Реальные clean-install/upgrade/uninstall и upload/publish GitHub Release не запускались в этом этапе: они относятся к финальной release-verification и не должны подменяться unit-тестами.
